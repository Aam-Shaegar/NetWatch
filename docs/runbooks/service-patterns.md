# Изменения поведения TCP-сервиса

Комплект для сервиса на TCP/8080 объединяет Isolation Forest, классификатор пауз и четыре проверки формы обмена. Он рассчитан на сервис с короткими соединениями. Метка описывает трафик в пятисекундном окне; она сама по себе не устанавливает причину сбоя. На сервисе с обычными большими ответами или постоянными соединениями требуется новый профиль.

| Метка в API | Что наблюдается |
|---|---|
| `foreground_pause` | Первая модель обнаружила отклонение, классификатор распознал приостановку основных запросов при сохраняющемся фоне. |
| `large_upload` | Входящие IP-байты в расчёте на активный поток превысили опорную границу. |
| `large_response` | Исходящие IP-байты на активный поток превысили опорную границу. |
| `connection_surge` | Число новых попыток TCP за пять секунд превысило опорную границу. |
| `persistent_exchange` | В окне ровно один активный поток, нет новых попыток TCP, прошло не менее восьми пакетов в каждом направлении. |

Числовые границы расширения равны 1,5 максимума соответствующей величины на обычных обучающих и калибровочных запусках базового детектора. Коэффициент 1,5 — инженерный запас. Признаки считаются по IP-байтам, включая заголовки; «на поток» означает отношение суммарных байтов к числу различных активных потоков в окне. Эти значения отличаются от размера тела HTTP-сообщения.

Если сработал признак длительного обмена, он получает приоритет. В остальных случаях берётся наибольшее отношение наблюдаемого значения к его границе. Если оно больше единицы, выводится соответствующая метка. Для роста объёма требуется одновременно превысить границу общего объёма по тому же направлению. Сила такого сигнала равна меньшему из двух отношений. Для этого решения в поле оценки записывается максимум оценки Isolation Forest и порога леса, умноженного на отношение. Для длительного обмена используется множитель 1,25. Рабочее правило открытия инцидента получает такое окно сразу, даже если лес пропустил изменение. Когда правила не срабатывают, решение остаётся за прежним детектором и классификатором пауз. Четыре новые метки имеют `probability: null`. У числа превышения и вероятности разные значения.

## Собрать и загрузить комплект

Из корня подготовленного проекта укажите каталоги базовой выборки и бинарного классификатора, полученные по [руководству по классификации](classification.md). Для сохранённых данных проекта команда выглядит так:

```sh
ml/.venv/bin/python -m netwatch_ml.training.service_patterns \
  data/processed/step7-16d38550a4d3 artifacts/step12-lab artifacts/tcp-service-patterns-v2
```

Команда проверяет контрольную сумму исходной модели и соответствие выборки. Результат записывается в новый каталог. Для существующего комплекта начните здесь:

```sh
export NETWATCH_MODEL_BUNDLE="$PWD/artifacts/tcp-service-patterns-v2/bundle.json"
export NETWATCH_MODEL_SHA256="$(python3 -c 'import json; print(json.load(open("artifacts/tcp-service-patterns-v2/report.json"))["bundle_sha256"])')"
export NETWATCH_MODEL_ID="$(python3 -c 'import json; print(json.load(open("artifacts/tcp-service-patterns-v2/report.json"))["model_id"])')"
export NETWATCH_POLICY_VERSION=v1
```

Запустите ML, API и worker с этим окружением по [инструкции сервера](server.md). Новые окна получат новую версию модели. Старые записи в журнале сохраняют первоначальные прогнозы.

## Воспроизвести испытание

Записи содержат только обычные локальные HTTP-запросы. В каждом контейнере клиент и сервис используют loopback. Контейнер запускается без внешней сети. Подготовьте образ лаборатории с помощью `make live-smoke`. Используйте новый выходной каталог и выполните из корня:

```sh
mkdir -p data/runs/pattern-replay
for seed in 2101 2102 2103 2104 2105 2106; do
  docker run --rm --network none --cap-drop ALL --cap-add NET_RAW \
    --cap-add SETUID --cap-add SETGID \
    -v "$PWD/lab/service_patterns.py:/lab/experiment.py:ro" \
    -v "$PWD/data/runs/pattern-replay:/output" netwatch-lab:dev \
    python /lab/experiment.py "/output/run-$seed" "$seed"
done
go build -o /tmp/netwatch-pattern-sensor ./cmd/netwatch-sensor
ml/.venv/bin/python scripts/audit_service_patterns.py \
  artifacts/tcp-service-patterns-v2 data/runs/pattern-replay /tmp/netwatch-pattern-sensor
```

Внутри каждого запуска порядок пяти изменений перемешан. Между ними выполняются обычные запросы, отмечаются фактические начало и конец фаз. Для проверки используется только окно целиком внутри интервала. Скрипт сверяет SHA-256 PCAP, счётчик потерь tcpdump, статусы декодирования и отсутствие повторного использования записи. Для эпизодного результата требуются два правильно названных окна среди трёх подряд внутри эпизода. Это измеряет повторяемое распознавание типа. Журнал может объединять соседние изменения в один инцидент до наступления условия закрытия.

## Результаты

На первых шести запусках все шесть пауз ошибочно получили метку роста исходящего объёма. При паузе остаются крупные фоновые ответы, поэтому их средний объём на поток высок. В окончательном правиле требуется также рост общего объёма окна. Суммарный порог составляет 52 528,5 входящего или 200 767,5 исходящего IP-байта. Границы на поток — 801,9 и 30 290,1 байта соответственно. Порог для новых соединений — 118,5 попытки за окно.

После фиксации исправленного комплекта записаны шесть новых запусков (seed 2101–2106), всего 125 795 пакетов. Эти запуски не использовались для настройки.

| Режим | Окон с правильным результатом | Подтверждено эпизодов |
|---|---:|---:|
| Пауза | 27 / 27 | 6 / 6 |
| Увеличение входящих байтов | 26 / 26 | 6 / 6 |
| Увеличение исходящих байтов | 24 / 24 | 6 / 6 |
| Всплеск новых соединений | 25 / 25 | 6 / 6 |
| Активный обмен в одном соединении | 26 / 26 | 6 / 6 |
| Обычная нагрузка | 111 / 111 штатных окон | 36 контрольных интервалов |

Обычная нагрузка представлена 555 секундами полных внутренних окон; в этих окнах не было тревог. На 481 нормальном тестовом окне базовой коллекции и на 17 окнах прежнего наплыва клиентов четыре новых правила также не сработали. Это последняя проверка именно расширения, отдельно от сигналов исходного леса. Переходы на границах фаз в таблицу не входят. Шесть эпизодов одного класса ограничивают точность оценки его полноты. При смешении причин возвращается одна метка. На другой сети потребуется самостоятельная проверка.

Для проверенной сборки идентификатор модели — `if-178d3c4067bbbfdaa1ae6ef1`. На одной диагностической записи проверены доставка окон, присвоение всех пяти меток, сохранение результатов в PostgreSQL и их русские названия в карточках браузера.
