# Классификация аномальных окон

Сначала Isolation Forest оценивает пятисекундное окно TCP-сервиса на порту 8080. Если оно аномально, вторая модель оценивает два известных состояния: обычная работа (`benign`) и пауза основного HTTP-клиента при продолжающемся фоновом трафике (`foreground_pause`). Класс описывает наблюдение в конкретном окне. Он не устанавливает причину инцидента. Вероятность относится к выбранному классу при распределении лабораторных данных.

В ответе API поле `classification` содержит метку, вероятность и версию классификатора. Низкая уверенность даёт `unknown`. Неполное окно или обнаруженные потери дают `insufficient_data`. Полное окно хоста либо другого сервиса вне проверенного профиля получает `unknown`; оценка аномальности в таком случае недоступна. При отказе вероятность равна `null`. Для нормального окна в рабочем профиле и для старых моделей отдельной классификации нет. Журнал показывает результат рядом со временем окна, экспорт сохраняет исходную запись.

## Воспроизведение

Из корня проекта сначала подготовьте набор и базовую модель по [руководству по данным](data.md) и [руководству по детектору](detector.md). Задайте переменные DATASET и BASELINE с путями к этим каталогам. Для восьми дополнительных размеченных запусков используйте изолированный Docker-стенд. Команда выводит каталог коллекции. Укажите его в CAPTURES. При новом сборе тайминги и статистики сети изменятся. Повторное обучение на сохранённых PCAP воспроизводит комплект побайтно.

```sh
python3 scripts/collect_dataset.py --classification --workers 1
go build -o /tmp/netwatch-classifier-sensor ./cmd/netwatch-sensor
ml/.venv/bin/python -m netwatch_ml.training.classification "$DATASET" "$BASELINE" /tmp/netwatch-classifier-sensor artifacts/classification "$CAPTURES"
python3 scripts/fetch_classification_samples.py data/raw/classification
ml/.venv/bin/python scripts/classifier_external.py data/raw/classification /tmp/netwatch-classifier-sensor artifacts/classification data/processed/classification-external
ml/.venv/bin/python scripts/incident_smoke.py artifacts/classification
```

Обучение проверяет контрольные суммы, принадлежность каждого запуска одной выборке и совпадение признаков при разборе PCAP Go-сенсором. Оба метода используют одинаковое разделение и предобработку базового детектора. Метод выбирается по average precision на validation. Отдельная выборка calibration сохраняет наблюдаемую долю пауз для сигмоидной калибровки. Порог выбирается на validation по максимальному покрытию при наблюдаемой ошибке среди принятых ответов до 5%. Версии и SHA-256 записываются в report.json. bundle.json содержит параметры обеих ступеней. reliability.svg сравнивает предсказанную вероятность паузы с наблюдаемой частотой до и после отбора первой ступенью. Старый комплект можно продолжать использовать независимо.

## Измерения в Docker

| Выборка | Окон | Из них пауза |
|---|---:|---:|
| Обучение | 1454 | 12 |
| Выбор метода и порога | 262 | 9 |
| Калибровка | 262 | 8 |
| Тест | 518 | 10 |

Логистическая регрессия выиграла у гистограммного градиентного бустинга по average precision. Порог уверенности составил 0,51549. В тесте классификатор отдельно правильно присвоил класс 508 обычным окнам и 10 окнам паузы. Через первую ступень прошли 13 окон, включая все 10 окон двух пауз. Precision и recall обоих классов на этих 13 окнах равны 1. Brier score составил 0,0000061 по всем окнам и 0,000212 после отбора. Покрытие составило 100% в обоих срезах. На обычном наплыве клиентов три из 17 окон преодолели порог аномальности, все три получили класс benign. Продолжительность этого наблюдения всего 85 секунд.

Событие в отчёте считается обнаруженным, если каскад правильно назвал хотя бы одно его окно. В отдельной сохранённой эксплуатационной записи шага 11 первая ступень пропустила все пять полных окон внутри размеченной паузы. Вторая ступень ни разу не получила эти окна. Поэтому результаты двух тестовых пауз нельзя переносить на произвольный HTTP-сервис. Правила формирования инцидентов и отдельная проверка сохранения результатов описаны в [руководстве журнала](incidents.md).

## Внешние записи

Из пятничного захвата CIC-IDS2017 извлекаются ограниченные фрагменты опубликованного расписания. Частичная копия WebDDoS CIC-DDoS2019 взята из открытой подборки PCAP. Каждый файл проверяется по SHA-256, обрабатывается офлайн тем же Go-сенсором. Окна, пересекающие разрыв записи больше пяти секунд, отбрасываются. Число пакетов относится к исходному фрагменту до отбора сущности. [Описание CIC-IDS2017](https://www.unb.ca/cic/datasets/ids-2017.html) · [Зеркало пятничного PCAP](https://huggingface.co/datasets/bvsam/cic-ids-2017) · [Описание CIC-DDoS2019](https://www.unb.ca/cic/datasets/ddos-2019.html) · [Подборка PCAP](https://zenodo.org/records/17121740)

| Сценарий | Сущность | Пакетов | Полных окон с unknown | Неполных с insufficient_data |
|---|---|---:|---:|---:|
| CIC-IDS2017, сканирование | Хост | 60 238 | 6 | 2 |
| CIC-IDS2017, DDoS | TCP-сервис на порту 80 | 17 681 | 3 | 2 |
| CIC-DDoS2019, WebDDoS | TCP-сервис на порту 80 | 3 104 | 39 | 2 |

Все 48 полных окон получили отказ по области применимости модели. Этот опыт проверяет поведение на другом порту и типе сущности. Он не измеряет способность распознать ранее неизвестную атаку на порту 8080. В словаре модели пока нет классов DDoS и сканирования. Для их выпуска нужны независимые размеченные эпизоды соответствующего профиля в обучении, калибровке и тесте, а также обычные всплески нагрузки тех же сервисов. Два отдельных DDoS-эпизода и один эпизод сканирования нельзя разделить между этими выборками без повторного использования события.

## Эксперимент с DDoS

Для проверки ложных DDoS-сигналов обучена отдельная логистическая регрессия. В её обучении 1418 обычных окон Docker и три окна одного эпизода CIC-IDS2017. Использованы общие числовые признаки сервиса, без IP и номера порта. Предобработка обучена на этих же данных. Действует стандартная граница решения модели. Эксперимент запускается отдельно от рабочего детектора, без изменения модели пилота.

Для воспроизведения укажите в CROWD_RUN каталог запуска из CAPTURES с seed 910. Внешние окна должны быть получены предыдущей командой аудита из проверенных PCAP.

```sh
ml/.venv/bin/python scripts/evaluate_ddos_candidate.py "$DATASET" data/processed/classification-external "$CROWD_RUN" /tmp/netwatch-classifier-sensor
```

Результат на обычном наплыве — 0 ложных решений DDoS из 17 окон за 85 секунд. Модель способна выдать DDoS: в обучающем эпизоде она присвоила эту метку трём окнам из трёх. На 39 полных окнах фрагмента независимого WebDDoS она ни разу не сработала. Метка внешней записи относится к сценарию в целом. Детальная разметка каждого из 39 окон отсутствует. Одно положительное обучающее событие из другого источника не позволяет отделить признаки атаки от особенностей стенда. Результат не даёт основания выпускать этот классификатор или показывать его балл как вероятность DDoS.

Для дальнейшей выборки есть также [открытые PCAP с фоновым трафиком хоста и сериями DDoS](https://zenodo.org/records/14049440). Авторы разделяют архивы по числу источников. Для использования в модели сервиса потребуется проверить транспорт, порт назначения, интервалы эпизодов и соответствие обычной нагрузки. Этот источник в приведённых числах не участвовал.
