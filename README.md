# NetWatch

NetWatch наблюдает сетевой трафик. Go-сенсор извлекает версионированные признаки из живого трафика и PCAP/PCAPNG. Для профиля `traffic-v3` сенсор передаёт наблюдения по gRPC с TLS. Анализатор сначала проверяет правила, затем направляет подходящие наблюдения в двухступенчатый Python-инференс. Инциденты сохраняются в PostgreSQL. Команда `netwatch` открывает меню статистики, сенсоров и тестирования.

Каталог v1 охватывает TCP-сканирование портов одного защищаемого узла, UDP flood и ICMP flood. Правила определяют наблюдаемые признаки этих событий. Качество на независимых трассах оценивается командами `make test-find`, `make test-classify` и `make test-pipeline`. [Каталог и разметка](docs/runbooks/catalog-v1.md)

**Статус v1 — экспериментальная версия.** На новых записях SSH-подбора временной детектор с прежним порогом обнаружил 571/575 окон, со сниженным — 571/575. На пяти часах штатного SSH сниженный порог дал 101 ложный инцидент, прежний временной порог и базовый малошумный RF — по нулю. Базовый RF остаётся рабочим кандидатом. [Проверка порога](benchmarks/v1-temporal-threshold.md) · [Проверка истории соединений](benchmarks/v1-temporal-ssh.md)

## Попробовать на записи

Из корня репозитория выполните команды ниже. Нужен Go версии из `go.mod`. При сборке под Linux с включённым CGO установите также заголовки libpcap. Команда читает небольшой PCAP из тестов. Для повторного запуска укажите новое имя выходного файла.

```sh
mkdir -p outputs
go run ./cmd/netwatch-sensor replay \
  --input tests/fixtures/pcap/syn-retry.pcap \
  --output outputs/windows.jsonl --host 192.0.2.10 --epoch fixture \
  --coverage-start 1700000000000000000 --coverage-end 1700000005000000000
cat outputs/windows.jsonl
```

В результате получится одно окно. Два исходящих SYN-пакета занимают 80 IP-байт и относятся к одной попытке соединения. Для разбора своей записи укажите адрес наблюдаемого хоста или параметр `--service IP:порт`. Границы наблюдения задаются в наносекундах Unix. Если их опустить, сенсор пометит покрытие как частичное. Без параметров хоста и сервиса команда `replay` выгружает метаданные отдельных пакетов. [Форматы захвата](internal/capture/README.md) · [Оконные признаки](contracts/features.md)

## Запустить на живом трафике

```sh
make bootstrap
make live-smoke
```

На macOS эти команды запускают сервис и сенсор внутри Docker Desktop. Сенсор наблюдает интерфейс тестового сервиса, пока клиент отправляет ему HTTP-запросы. В конце проверка сравнивает статистику живого трафика со статистикой повторного чтения той же записи. Результаты сохраняются в каталоге запуска под `data/runs/`. Нативный сенсор Linux и macOS использует libpcap. Запускайте его на разрешённом интерфейсе наблюдаемой системы. [Подготовка окружения](docs/runbooks/development.md) · [Настройка интерфейса и фильтра](docs/runbooks/live.md)

## Запустить серверный стек

Подготовьте `.env.work` по [инструкции сервера](docs/runbooks/server.md) и выполните `make work`. Команды `make work-status`, `make work-logs` и `make work-stop` управляют работающим стеком. Постоянный том PostgreSQL сохраняется при пересоздании контейнера. [Резервное копирование и восстановление](docs/runbooks/server.md#резервное-копирование-и-восстановление)

Соберите `make cli` и запустите `bin/netwatch`. Для статистики и управления сенсорами укажите адрес сервера, доверенный сертификат и файл операторского токена. Из раздела **Сенсоры** можно получить одноразовый код для `netwatch-sensor enroll`, приостановить работу сенсора и отозвать доступ. Из раздела **Тестирование** можно запустить оценки на подготовленных данных прямо в терминале. [Настройка клиента и сенсора](docs/runbooks/server.md#диагностика-из-терминала)

Для первой регистрации запустите `netwatch-sensor enroll` с параметрами подключения из инструкции сервера. Сенсор запросит код в терминале и скроет ввод. При запуске без подкоманды сенсор выводит справку.

## Лабораторный профиль прежних версий

1. Соберите размеченные запуски и экспортируйте окна командой `make dataset`. Сохраните путь к выходному каталогу. [Сбор данных](docs/runbooks/data.md)
2. Обучите Isolation Forest командой `make train DATASET=… OUTPUT=…`. В выходном каталоге появятся `bundle.json` и `report.json`. Если у вас уже есть проверенный комплект, используйте его путь, идентификатор и SHA-256. Веса хранятся отдельно от исходников. [Загрузка модели](docs/runbooks/detector.md)
3. Запустите PostgreSQL, примените миграции и укажите одинаковый идентификатор модели для API и worker. Настройте ключи сенсора и оператора перед запуском API. Отправьте окна через очередь сенсора. [Запуск процессов](docs/runbooks/server.md) · [Доставка окон](docs/runbooks/delivery.md)
4. Откройте журнал на `http://127.0.0.1:8080/`. В карточке инцидента доступны время, признаки и оценки по каждому окну. Для сквозной проверки на своей машине предусмотрен сценарий с настоящим браузером. [Открыть и проверить журнал](docs/runbooks/incidents.md)

## Результаты лабораторного профиля

Для прежнего лабораторного профиля `traffic-v1` используется детектор NetWatch на базе Isolation Forest с политикой инцидентов `v2`. Оператор указывает путь к комплекту и SHA-256 в `.env.work`. MLP включён в сравнение кандидатов. [Результаты сравнения](benchmarks/detection-results.md)

Лабораторная модель проверена для одного TCP-сервиса на порту 8080. Isolation Forest отмечает отклонения. Классификатор пауз различает обычную работу и паузу основных запросов при продолжающемся фоне. Расширенный комплект также отмечает рост входящих или исходящих байтов на поток, всплеск новых TCP-соединений и активный обмен в одном длительном соединении. [Настройка, значения меток и результаты испытания](docs/runbooks/service-patterns.md). Плохое покрытие окна, неподдерживаемый профиль или низкая уверенность отражаются в результате.

В пилоте обработано 6 664 окна за несколько периодов наблюдения. Единственный зарегистрированный инцидент совпал с запланированной паузой. В отдельном эксперименте DDoS-кандидат пропустил независимый эпизод WebDDoS, поэтому продукт не выдаёт вероятность DDoS. [Результаты пилота](docs/runbooks/operations-results.md) · [Классификация](docs/runbooks/classification.md) · [Сравнение с прогнозом GRU](docs/runbooks/forecast-results.md)

## Код

| Каталог | Назначение |
|---|---|
| `cmd/`, `internal/` | Сенсор, разбор пакетов, статистика соединений, API и обработчик заданий |
| `ml/` | Подготовка выборок, обучение и сервис прогнозирования |
| `contracts/`, `migrations/` | Форматы обмена и схема PostgreSQL |
| `web/` | Журнал инцидентов на React и TypeScript |
| `deploy/`, `lab/`, `scripts/` | Docker-стенд, клиенты и воспроизводимые проверки |
| `netwatch/`, `examples/` | Первоначальный автономный Python-прототип и пример входных данных |

Основные проверки запускаются через `make test build compose-check`. Для проверки очереди, базы и выдачи прогнозов используйте `make server-smoke`.
