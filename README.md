# NetWatch

NetWatch наблюдает сетевой трафик выбранного хоста. Сенсор на Go собирает пятисекундные окна и передаёт их по gRPC с TLS. Анализатор применяет правила, затем ML, сохраняет инциденты в PostgreSQL и показывает их в терминале.

**Текущая версия предназначена для серверного пилота.** Каталог включает TCP-сканирование портов, UDP flood и ICMP flood. Для SSH-подбора возможна тревога `unknown`. Поставляемый профиль использует малошумный Random Forest и временной детектор с порогом `0.9978790881906234`. Веса входят в репозиторий. [Архитектура](docs/architecture.md) · [Каталог и условия обнаружения](docs/runbooks/catalog-v1.md)

## Запуск на одном сервере Linux

Нужны Git, Docker Engine с Compose v2, Make, Python 3 и OpenSSL с поддержкой `-addext`. Определите интерфейс и защищаемый IP командой `ip -br addr`. Подставьте их вместо примера ниже.

```sh
git clone --branch main --single-branch https://github.com/Aam-Shaegar/NetWatch.git
cd NetWatch
PILOT="$HOME/.netwatch-pilot"
python3 scripts/init_pilot.py "$PILOT" --interface eth0 --host 192.0.2.10
make work WORK_ENV="$PILOT/work.env"
```

Эти команды запускают анализатор и базу. Чтобы начался захват, зарегистрируйте сенсор через терминальное меню, запустите контейнер `sensor-v1` и проверьте поступление первых полных окон командой `netwatch doctor`. Одноразовый код вводится в приглашении сенсора. [Команды регистрации, запуска и проверки](docs/runbooks/server.md#пилот-на-одном-сервере-linux)

## Проверки

| Задача | Команды | Что потребуется |
| --- | --- | --- |
| Проверить код, сборку и конфигурацию | `make bootstrap`, затем `make test build compose-check` | [Окружение разработки](docs/runbooks/development.md) |
| Проверить доставку, очередь и запись решений | `make server-smoke` | Docker и подготовленное окружение |
| Сверить живой захват с повторным чтением записи | `make live-smoke` | Локальный Docker-стенд |
| Измерить качество обнаружения, классификации и конвейера | `make test-find`, `make test-classify`, `make test-pipeline` | Размеченная выборка и каталог обученных кандидатов. [Подготовка входов и параметры](docs/runbooks/v1-evaluation.md) |

Оценка кандидатов доступна также в меню **Тестирование**. Для запуска самого сервера исследовательские датасеты не нужны.

## Как выбирали модель

| Эксперимент | Что проверяли |
| --- | --- |
| [Первое сравнение](benchmarks/v1-model-comparison.md) и [независимый тест](benchmarks/v1-blind-test.md) | Сравнили детекторы и классификаторы, затем проверили связки RF → RF и GB → RF на новых захватах. |
| [Разбиение по источникам](benchmarks/v1-source-held-out.md) и [проверка чувствительности RF](benchmarks/v1-sensitivity-test.md) | Измерили, как меняются пропуски, верно определённые типы и ложные инциденты на других сетях. |
| [История соединений](benchmarks/v1-temporal-ssh.md) и [выбор порога](benchmarks/v1-temporal-threshold.md) | Сопоставили однооконный RF и до шести окон истории, зафиксировали порог до независимого теста и проверили выбранный вариант в приложении. |

В последнем архивном тесте оба временных порога обнаружили **571 из 575** окон SSH. За **130,54 хост-часа** штатных записей прежний порог дал **0** ложных инцидентов, сниженный — **124**. В строгом серверном прогоне с измеренными потерями приложение обнаружило **60/60** размеченных SSH-окон и дало **0** ложных тревог на **2 170** штатных окнах. Архивный тест допускает неизвестное число потерянных пакетов. В серверном профиле такое окно получает `insufficient_data`.
